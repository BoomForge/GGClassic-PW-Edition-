# Native third-person gameplay — owner priority

## Goal
A proper engine-supported third-person mode, not a gameplay script attached to an entity. Preserve existing first-person projects and existing Classic third-person marker compatibility.

## First source stage
The existing `tpp/thirdperson.lua` file is an empty marker. The real legacy camera/facing code is in `gameplayercontrol.lua`. The new native binding replaces that section when a valid non-VR single-player third-person avatar is active. C++ calculates orbit, shoulder offset, facing, nearest collision restriction and frame-time smoothing. The protagonist uses the existing physics body rather than a new duplicate player. Legacy fallback remains for incompatible binaries and `GGCPW_LEGACY_THIRDPERSON=1`. The modified stock controller must be copied and exported with the engine (build copy and existing export collection). Full engine build and actual runtime checks are pending.

## Owner clarification — combat and interaction are the acceptance gate (25 November 2026)

The owner recalls the existing mode being limited by lack of usable combat and interaction. A prettier camera is not sufficient. Prioritise these gameplay capabilities alongside the minimum movement/animation foundation, ahead of cosmetic camera polish.

Confirmed code findings (not yet reproduced in Windows gameplay):
- `G-Gun.cpp::gun_change` explicitly returns for an already-equipped third-person character ("cannot equip new weapons for the moment"). Weapon pickup/equip/unequip/switch, ammunition, inventory and attachment lifecycle must be integrated rather than merely removing the return.
- Existing melee uses horizontal range, height and facing checks but no obstruction test in the strike loop. It also calculates `rand()%iDamageRange`, which is invalid when minimum and maximum damage are equal. Fix damage range, target eligibility, obstruction, animation strike windows and one hit per target per swing. Add unarmed, sword and other melee tests.
- Existing ranged code uses a special camera ray (unlocked view), a hard-coded short range for locked view, and a separate third-person projectile attachment path. Design a coherent aim-target-to-muzzle trajectory with obstruction checks, configured range, aim alignment, hit attribution and reticle behaviour.
- `M-LUA-Entity.cpp::entity_lua_getentityplrvisible` temporarily hides the protagonist to avoid self-intersection in door scripts. Replace fragile self-hit handling with an explicit player-body/interaction origin and exclusion policy; keep true camera queries separate. Validate range, visibility, occlusion, nearest target and action input, including doors, switches, pickups, NPC conversations, chests, quest objects, triggers and interaction prompts.
- Preserve existing first-person APIs and legacy Lua scripts where possible. Provide a semantic interaction API and make the remappable interact action usable from both modes.

**Acceptance gate:** one small playable test level with a third-person character able to walk/run, interact with doors, talk to an NPC, collect items, equip/switch weapons, attack a damageable enemy with melee and ranged weapons, reload, take damage, die/respawn and save/load. Obstructed interactions and attacks must not pass through walls, and the camera's position must not determine gameplay reach. Test both first-person and third-person modes on Windows. Source audit is not a claim these repairs are already implemented.

## Combat and interaction source progress — 25 November 2026

Implemented shared C++ player-origin, live entity target and terrain/entity obstruction queries (`PW-ThirdPersonGameplay.h`, `G-Entity.cpp`). Third-person legacy door visibility now excludes the protagonist by object ID and uses the actual physics body instead of toggling visibility. Rotate/look-at-player calls use explicit player position. Added `PWCanInteract(e, range)` boolean Lua query for new scripts (valid active visible target, living player, reach and line-of-sight; does not itself activate the target). Melee now consumes one strike per new swing, chooses nearest eligible target within an arc/height/reach, rejects blocked targets, uses live transforms and fresh impact coordinates, and supports fixed or reversed damage ranges safely. Weapons with a configured projectile are not automatically classified as melee by the legacy bow/axe/sword status codes. Added isolated geometry/damage tests. Build and gameplay checks pending. Static merged door meshes, animation frame skipping, character creator child meshes and unusual character rigs need specific real-world validation.

The equip/switch restriction is NOT removed yet: attachment creation currently uses the shared FPE's weapon name, not the per-instance current weapon ID, and the gun manager overwrites its selected weapon from the protagonist's fixed profile. Next work must integrate the attachment lifecycle and equipped slot together, not just remove a guard. Ranged camera-to-muzzle aiming, projectile pitch, melee animation state transitions, context interaction target/action dispatch and native movement remain open.

## Weapon switching and attachment lifecycle — 25 November 2026

Removed the hard-coded third-person equip return and the gun-manager assignment from the authored entity weapon. Existing owned inventory slots, number keys, scroll selection and holster use the normal gun-change flow. A native preflight requires a valid protagonist, owned preloaded HUD weapon, actual vweap.x/DBO and valid hand firespot. The replacement world model loads in a staged reusable attachment ID before the previous one is removed; only the protagonist instance's equipped weapon is changed, never its shared FPE profile. Holster clears the attachment and weapon ID. Existing ammo slots are not reset. Failed preflight leaves the old weapon, and repeated switches recycle attachment IDs. Added isolated equip eligibility checks.

Limitations: supports existing Classic-compatible hand firespot rigs and preloaded weapons only; arbitrary new/missing HUD weapons (including some cross-level profile restores), asset discovery/export packaging, dead-NPC weapon pickup, custom bone/socket authoring and per-weapon character animations remain open. Not a claim of live success; verify first equip, slot changes, holster/re-equip, ammo/reload, missing asset rejection, old attachment deletion, repeated switching and NPC instances sharing the FPE. Next: native aim target/muzzle obstruction and projectile pitch, then animation and interaction dispatch.

## Ranged combat source stage — 25 November 2026

Shared native aim resolution uses existing third-person reticle coordinates (50%, 25%) for free camera, character-forward for locked camera, closest terrain/entity aim point, actual VWEAP muzzle or hand socket, body-to-muzzle clearance, and configured gun range. A captured shot retains muzzle/direction across delayed pellet iterations and rejects changed gun/firemode. Hitscan damage still passes through Classic's ordinary muzzle-origin bullet collision path; projectiles use the same aim direction and retain pitch/yaw instead of being overwritten by hidden HUD limbs, legacy camera pitch or automatic targeting. Player projectile spawn no longer skips unchecked world space, and direct ray collision explicitly excludes the protagonist for player-fired projectiles. Gunfire AI alert originates at the player. Added isolated vector/angle/zero-distance/range tests.

This is source work; test actual VWEAP limb orientation and update timing, reticle alignment, close walls/corners, locked camera, projectile gravity and collision modes, spread/piercing, missing muzzle, damage attribution, weapon switches mid-burst and first-person regressions. Blocked muzzle may still consume ammo because preflight occurs at the existing shot dispatch point. Reticle graphics/aim animation, advanced sockets, projectile lifetime range and full runtime acceptance remain open. Next: native movement and animation coordination, plus contextual interaction dispatch.

## Native locomotion and animation coordination — 25 November 2026

Native C++ movement decision now consumes Classic's gathered/remapped digital actions; cancels opposite directions, computes camera-relative heading, supports directional free movement, sprint and slower RMB aiming/strafe/backpedal. Both held mouse buttons are recognised for aiming. Native animation coordinator uses existing char_loop with the verified protagonist index/object, movement-state codes, animation speed and validated jump hold frame; scripted legacy branch remains for unsupported builds/modes. Existing physics frequency scaling is retained through the base-speed setter. Camera facing now follows actual permitted movement rather than raw keyboard presses during cutscenes/death. Added deterministic movement, strafe, cancellation and jump-hold tests. Prior ranged build and isolated tests passed; this revision requires its own validation.

This does not yet replace every shared Lua physics policy: acceleration, jump impulse, gravity, slope, water and footfalls still use the established controller. Crouch remains disabled in the existing TPP input path until compatible crouch animations and capsule transitions are integrated; custom per-weapon animation mapping, controller analog movement and explicit land/fall states need work. Next priority is contextual interaction targeting and action dispatch, then native editor mode/lifecycle and actual test-level acceptance.

## Contextual interactions — 25 November 2026

The prior movement revision d2bdbdcf passed all 11 GitHub workflows, including full Windows compilation. This source stage adds one native contextual target per Lua frame for supported single-player TPP. The player-body position, character facing, live target bounds, visibility, reach, terrain and geometry line-of-sight determine eligibility; nearer and more forward targets are preferred, with deterministic entity-ID tie breaks. Remapped E/controller Y produces one rising-edge press for the selected target; holding the action while turning, entering a level or exiting a cutscene cannot trigger a second target. The first-person path and non-participating scripts retain raw key state.

Stock door, switchmain, doorswitch, doorswitchanimate and lightswitch script calls receive scoped key dispatch and non-target Prompt/PromptDuration suppression via global.lua; stock keys and weapons now use explicit contextual pickup rather than automatic key collection or first-person-only weapon pickup. Existing ammo/health pickups retain their proximity behavior, physics carrying is unchanged, and arbitrary legacy scripts are not silently converted. Custom NPC/chest/quest scripts can opt in by naming their script/function prefix pw_interact_ (for example pw_interact_chest.lua with pw_interact_chest_main(e)), using PWInteractionFocused(e) for prompts and PWInteractionPressed(e) for a single activation. Range is 150 engine units for custom scripts and 100–150 for stock scripts. Actual dialogue, chest inventory and custom editor properties remain game-specific and are not included. Old binaries and GGCPW_LEGACY_THIRDPERSON=1 retain prior paths. Stock door/switch prompts may still say E rather than the remapped key.

The build copy, native C# updater and Python/PowerShell package allowlists now include key.lua, weapon.lua and the previously omitted gameplayercontrol.lua. Release manifests must explicitly include updated scripts. Existing player-customised scripts should be backed up before distribution. Isolated tests cover range/facing, deterministic ordering and press/release lifecycle; Windows build and actual door, overlapping targets, locked door, weapon pickup/full inventory, NPC/chest script, pause/respawn, obstruction and first-person regression tests remain pending. Stock scripts that are not listed, physics object carrying, editor selection, custom animation maps and live acceptance remain open.

## Remaining implementation order
1. Trace native physics movement and animation state contracts; extract third-person-specific movement and animation orchestration from Lua without changing first-person.
2. Native camera-relative movement, turning, free orbit, aiming/strafing, sprint/crouch/jump/fall/land, slope and wall collisions; configurable camera sensitivity, distance, shoulder and target framing. Camera override and indoor clearance tests.
3. Combat and interaction (highest gameplay priority, develop in parallel with the minimum movement/animation foundation): camera aim target with muzzle/hand obstruction, melee, ranged projectiles, hit attribution, equip/switch and weapon attachments; shared interaction origin, semantic action, line of sight, target selection and stock door/pickup/NPC compatibility. No shooting or interacting through walls.
4. Explicit editor player mode and protagonist model selection, rig/animation mapping and preview; integrate existing player settings and importer/character creator roadmap. No required entity gameplay script.
5. Player death/ragdoll/respawn, checkpoints, teleports, level transitions and persistent profiles; character and weapon state restoration.
6. Acceptance: actual editor and exported Windows game with a licensed character, first-person regression, low/high FPS, walls and corners, stairs, terrain, aim, melee, ranged, all locomotion states, custom model, death/respawn and save/reload. Validate update packaging and do not mark full native support complete until owner testing.

Current limitations: Lua still owns animation, movement and combat policy, camera callbacks rely on updated shared controller, static clearance rays are not a true sphere cast and dynamic obstacles/aim alignment need further work. No new model or proprietary media added.
